# AGENTS.md

## Project Overview

This repository is a React Native boilerplate using Expo prebuild, TypeScript, Zustand, TanStack React Query, Gluestack UI, NativeWind, and Expo Updates.

The project is not a pure managed Expo app. Native iOS and Android projects are generated by Expo prebuild, then extended by config plugins to support multiple environments.

Core assumptions:

- Package manager: `pnpm`
- Runtime: Node.js `>=22.11.0`
- Expo SDK: `56`
- React Native: `0.85.3`
- Environment source of truth: `app.config.ts`
- Native environment generation: `plugins/with-environment-support.cjs`
- Runtime app config access: `src/shared/config/appConfig.ts`
- OTA update docs: `docs/EXPO_UPDATES.md`

## Mandatory First Steps

Before planning or editing:

1. Read `README.md`.
2. Read this `AGENTS.md`.
3. Read relevant docs under `docs/` when touching environment, OTA, native build, or release flow.
4. Inspect existing files before making assumptions.
5. Keep changes minimal and consistent with current project patterns.

## Package Manager Rules

Use `pnpm` only.

Allowed examples:

```bash
pnpm install
pnpm lint:tsc
pnpm eslint app.config.ts
pnpm prebuild:clean
pnpm android
pnpm ios
```

Do not introduce or use:

```bash
npm install
yarn
yarn.lock
.yarnrc.yml
```

The expected lockfile is `pnpm-lock.yaml`.

## Environment Model

Supported environments:

- `development`
- `staging`
- `production`

Environment files:

- `.env`
- `.env.staging`
- `.env.production`

Important variables:

```env
APP_VARIANT=development|staging|production
APP_NAME=Dev|Staging|Production
API_URL=https://example.com
VERSION_CODE=1
VERSION_NAME=1.0.0
EXPO_PROJECT_ID=...
EXPO_UPDATE_URL=https://u.expo.dev/...
EXPO_UPDATE_CHANNEL=development|staging|production
```

`APP_FLAVOR` may exist as a legacy alias, but new code should use `APP_VARIANT`.

## Expo Config Rules

`app.config.ts` is the source of truth for:

- app variant metadata
- iOS bundle identifiers
- Android application IDs
- display names
- native version fields
- Expo Updates metadata
- runtime `extra` values
- branding asset paths

Do not hardcode environment behavior in application code if it belongs in `app.config.ts`.

JS runtime code should read app config through:

```ts
import { appConfig } from '@/shared/config/appConfig';
```

Avoid reading `process.env` directly in app runtime code unless there is a deliberate reason.

## Native Generation Model

`pnpm prebuild:clean` runs:

```bash
expo prebuild --clean
```

This deletes and regenerates `ios/` and `android/`.

The project must remain reproducible after `pnpm prebuild:clean`.

The config plugin at `plugins/with-environment-support.cjs` regenerates native environment support:

- Android product flavors: `development`, `staging`, `production`
- Android default flavor: `development`
- Android variants: `developmentDebug`, `stagingDebug`, `productionDebug`
- iOS default development scheme: `NewReactNativeZustandRNQ`
- iOS explicit schemes: `Staging`, `Production`
- iOS explicit configurations: `Staging.Debug`, `Staging.Release`, `Production.Debug`, `Production.Release`
- Podfile project configuration mappings
- iOS build settings for `APP_VARIANT`, `ENVFILE`, bundle id, display name, and version
- Android Gradle task environment injection for `expo-constants`

## Native Editing Rules

Treat `ios/` and `android/` as generated output unless the user explicitly chooses a bare-native workflow.

Do not place important custom native code only inside generated files if it must survive `prebuild --clean`.

Use these approaches instead:

- Config plugin for native configuration changes: plist, manifest, Gradle, Podfile, schemes, build settings, permissions.
- Local Expo module for Swift/Kotlin native bridge code.
- `assets/branding/` for app icon and splash source assets.

If a required change is made directly under `ios/` or `android/`, also add the corresponding config plugin or documented regeneration step, otherwise the change is fragile.

## Native Bridge Guidance

For custom native APIs exposed to React Native, prefer a local Expo module outside generated native folders:

```txt
modules/
  my-native-feature/
    expo-module.config.json
    ios/
    android/
    src/
```

The app can import the module through a TypeScript wrapper. Expo autolinking should reconnect it during prebuild/build.

Use config plugins for wiring and local Expo modules for real Swift/Kotlin implementation.

## Build Commands

Development:

```bash
pnpm android
pnpm ios
```

Staging:

```bash
pnpm android:stg
pnpm ios:stg
```

Production:

```bash
pnpm android:prod
pnpm ios:prod
```

Regenerate native folders:

```bash
pnpm prebuild:clean
```

Do not reintroduce separate prebuild scripts like:

```bash
prebuild:clean:stg
prebuild:clean:prod
```

The native project should contain all environments after one clean prebuild.

## IDE Build Mapping

Xcode:

- Development: scheme `NewReactNativeZustandRNQ`, configuration `Debug`
- Staging: scheme `Staging`, configuration `Staging.Debug`
- Production: scheme `Production`, configuration `Production.Debug`

Android Studio:

- Development: `developmentDebug`
- Staging: `stagingDebug`
- Production: `productionDebug`

Android keeps a `development` product flavor because once Gradle flavor dimensions exist, every environment needs a flavor. The development flavor is marked as default.

## Versioning Rules

Native version values come from the selected env file:

- Android: `versionCode`, `versionName`
- iOS: `CURRENT_PROJECT_VERSION`, `MARKETING_VERSION`
- JS runtime: `extra.versionCode`, `extra.versionName`

After changing `VERSION_CODE` or `VERSION_NAME`, run:

```bash
pnpm prebuild:clean
```

Then build the target variant.

## Expo Updates Rules

Read `docs/EXPO_UPDATES.md` before changing OTA behavior.

Important constraints:

- OTA updates only apply to compatible native binaries.
- `runtimeVersion` is tied to `VERSION_NAME`.
- `EXPO_UPDATE_CHANNEL` should usually match `APP_VARIANT`.
- OTA is disabled in `__DEV__`.
- Native dependency or config changes require a new native build.

Use:

```bash
pnpm update:push
pnpm update:list
pnpm update:check
pnpm update:test
```

## Source Structure

Primary source folders:

- `src/app/`: providers and app-level state setup
- `src/data/`: API, HTTP client, persistence, infrastructure services
- `src/presentation/`: screens, navigation, hooks, UI
- `src/shared/`: config, constants, models, types, utilities

Keep layer boundaries clear:

- UI should not own API client details.
- Data services should not own screen behavior.
- Shared code should stay generic and reusable.
- Environment access should go through shared config.

## Code Style

General rules:

- TypeScript first.
- Prefer existing patterns over new abstractions.
- Keep changes small and focused.
- Avoid unrelated refactors.
- Do not commit secrets or real credentials.
- Keep generated native changes reproducible through config.

Formatting and checks:

```bash
pnpm lint
pnpm lint:fix
pnpm lint:tsc
pnpm test
```

For targeted work, run the smallest useful verification, for example:

```bash
pnpm eslint app.config.ts plugins/with-environment-support.cjs
pnpm lint:tsc
```

## Dependency Rules

Before adding a dependency:

- Check whether the project already has an equivalent package.
- Prefer Expo-compatible packages for native functionality.
- For native packages, confirm they support Expo prebuild and React Native `0.85.3`.
- Run `pnpm install` after dependency changes.
- Verify that `pnpm prebuild:clean` still succeeds if the dependency affects native code.

Do not add `react-native-config`; this project intentionally uses Expo-native config.

## Generated Assets

Branding source assets live in:

```txt
assets/branding/
```

Expo prebuild regenerates platform-specific assets from those source files.

Do not rely on manual edits to generated app icon or splash files under `ios/` or `android/`.

## Git And Worktree Safety

The worktree may already be dirty.

Rules:

- Do not revert user changes unless explicitly asked.
- Do not run destructive git commands like `git reset --hard` or `git checkout --` without explicit approval.
- Do not amend commits unless explicitly asked.
- If generated native files change after `prebuild`, explain that they were regenerated.
- If unrelated files are dirty, ignore them.

## Verification Checklist

Use the checklist that matches the change.

For TypeScript/app code:

```bash
pnpm lint:tsc
pnpm eslint <changed-files>
pnpm test
```

For Expo config/plugin/native generation:

```bash
pnpm prebuild:clean
pnpm lint:tsc
pnpm eslint app.config.ts plugins/with-environment-support.cjs
xcodebuild -list -project ios/NewReactNativeZustandRNQ.xcodeproj
cd android && ./gradlew :app:tasks --all
```

For Android env verification:

```bash
cd android
APP_VARIANT=development ./gradlew :app:processDevelopmentDebugResources -x lint -x test
APP_VARIANT=staging ./gradlew :app:processStagingDebugResources -x lint -x test
```

For iOS env verification:

```bash
xcodebuild -showBuildSettings -project ios/NewReactNativeZustandRNQ.xcodeproj -scheme NewReactNativeZustandRNQ -configuration Debug
xcodebuild -showBuildSettings -project ios/NewReactNativeZustandRNQ.xcodeproj -scheme Staging -configuration Staging.Debug
xcodebuild -showBuildSettings -project ios/NewReactNativeZustandRNQ.xcodeproj -scheme Production -configuration Production.Debug
```

Check for:

- `APP_VARIANT`
- `ENVFILE`
- `APP_DISPLAY_NAME`
- `PRODUCT_BUNDLE_IDENTIFIER`
