# React Native Zustand React Query — Project Overview & PDR

## Project Purpose

This is an opinionated, production-ready React Native boilerplate template designed to accelerate cross-platform mobile app development. It provides a modern architecture with clean separation of concerns, comprehensive type safety, and a well-documented native build pipeline. The template is published and distributed via the [create-rn-project](https://github.com/linhnguyen-gt/create-rn-project) CLI for rapid project initialization.

## Primary Goals

- **Developer Experience:** minimize setup friction and onboarding time for new projects
- **Type Safety:** enforce strict TypeScript throughout to catch errors at compile time
- **Architectural Clarity:** demonstrate proven patterns for state, API, and error handling
- **Multi-Environment Support:** seamless development, staging, and production builds via Expo prebuild
- **Maintainability:** modular structure with high test coverage on critical paths
- **Native Customization:** Expo config plugins for reproducible native generation without manual edits

## Target Users & Scope

- Mobile app developers building cross-platform apps (iOS/Android)
- Teams adopting Zustand + React Query for state management
- Projects requiring multi-environment (dev/staging/prod) support
- Developers valuing strict type safety and automated testing

Intentional scope boundaries:
- **Not** a minimal template — includes testing, linting, and error handling infrastructure
- **Not** a framework — teaches patterns that work with Expo, Prebuild, and managed updates
- **Not** unopinionated — chooses specific libraries (Zustand, React Query, NativeWind) and enforces conventions
- **Does not** dictate screen-building patterns; examples show different idioms (both hook and imperative navigation exist today)

## Key Architectural Decisions & Rationale

### 1. Zustand + React Query Split

- **Zustand** stores client state (UI filters, counters, feature flags, user preferences) with zero middleware by default.
- **React Query** owns server state (API responses) with automatic deduplication and background refetching.
- **Rationale:** Keeps concerns separate, makes server state refetching explicit, and reduces store complexity.
- **Trade-off:** Developers must consciously choose where data belongs; incorrect placement is an anti-pattern.

### 2. Expo Prebuild + Config Plugin Over Manual Native Edits

- Native iOS and Android directories are generated by `expo prebuild --clean` and committed to `.gitignore`.
- Env-specific native config (bundle IDs, package names, schemes, flavors) is generated by the Expo config plugin (`plugins/with-environment-support.cjs`).
- **Rationale:** Reproducibility — rebuilding from scratch always produces identical native output; no drift from manual edits.
- **Trade-off:** Requires discipline to use the plugin for native changes; ad-hoc edits in ios/ or android/ are lost on the next prebuild.

### 3. Throw-Not-Degrade Config Validation

- Missing or invalid `API_URL`, `APP_VARIANT`, `VERSION_NAME`, or `VERSION_CODE` causes app startup to fail loudly with a clear error.
- **Rationale:** Misconfigurations should not silently fall back to development defaults; a production build hitting a dev API is worse than a crash.
- **Trade-off:** local dev and IDE builds need the values present. EAS holds them (`pnpm env:pull`, `pnpm env:exec`); `.env` files are the offline copy, seeded by `pnpm env:setup`. CI copies `.env.example`.

### 4. Dev-Only Reactotron via Inline Require

- Reactotron is loaded only in `__DEV__` via an inline `if (__DEV__) require(...)` in App.tsx bootstrap.
- Metro bundler tree-shakes it entirely in release builds.
- **Rationale:** No runtime performance cost; prod binary does not carry debug tooling.
- **Trade-off:** Requires explicit inline require; Reactotron cannot be imported as a normal module without risking inclusion in release builds.

### 5. Hand-Rolled `tv()` Replacing tailwind-variants Library

- Custom `tv()` implementation in `src/shared/style/tailwind-variants.ts` provides variant system without external dependency.
- Uses twMerge for class conflict resolution.
- **Rationale:** Avoids dependency bloat for a simple utility; encourages smaller, focused styling approach.
- **Trade-off:** No compound variants via `compoundVariants` key; developers must hand-roll multi-prop logic if needed.

### 6. SecureStore-Only Persistence

- Sensitive data (refresh tokens) goes to expo-secure-store with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` accessibility.
- No AsyncStorage persistence layer; client state (Zustand) is session-scoped.
- **Rationale:** Clear security boundary; secrets never touch plain storage. Session-scoped state forces explicit logout and state reset.
- **Trade-off:** No automatic persistence of user preferences or UI state; designers must choose what survives app restart and implement it explicitly.

### 7. Single HTTP Client Instance with Token Refresh Dedupe

- HttpClient is a singleton with request-level rate limiting, request validation, and session-aware token refresh.
- Refresh requests go on a separate, interceptor-free axios instance to prevent circular refresh loops.
- Single-flight dedupe ensures concurrent 401s trigger only one refresh, with ABA-safe epoch guards.
- **Rationale:** Centralized error handling, rate limiting, and session management reduce bugs; single-flight prevents thundering herd on token expiry.
- **Trade-off:** Complex interceptor logic; subtle epoch-based ABA defense required to avoid race conditions.

## Non-Goals & Exclusions

- **Offline-first architecture:** No sync engine; offline scenarios require explicit application logic.
- **Analytics / crash reporting:** Sentry hook exists but is a TODO stub; projects integrate their own instrumentation.
- **In-app messaging / push notifications:** Left to project-specific needs.
- **Payment / subscription flows:** Not included; projects integrate payment providers separately.

## Success Criteria

A project using this template should achieve:

- **Onboarding:** Developer new to the repo understands architecture and can add a screen + API call + test within 1 hour.
- **Type safety:** `pnpm lint:tsc` passes with zero errors in strict mode.
- **Quality gates:** `pnpm test:ci` enforces coverage thresholds (statements 58%, branches 45%, functions 51%, lines 59%).
- **Native reproducibility:** `pnpm prebuild:clean` produces identical output across runs and developers.
- **Multi-env:** `pnpm ios:stg` and `pnpm android:prod` build correct bundle/package IDs and connect to the right API URL without manual intervention.

## Constraints & Dependencies

- **Node >= 22.11.0** (enforced in .nvmrc)
- **pnpm 10.33.0** via Corepack
- **Expo SDK ~57.0.8** (tracks Expo's pinned versions for dependencies)
- **React Native 0.86.0** (New Architecture, Fabric, TurboModules, Hermes required)
- **iOS 16.4+** deployment target (set by plugin)
- **Android API 24+** min SDK
- **CocoaPods** and **Ruby** for iOS builds
- **Android Studio + Gradle** for Android builds

## Deployment & Distribution

The template is published as a git repository and distributed via the **create-rn-project** CLI. Developers run:

```bash
npx create-rn-project my-app
```

This clones the template and prompts for customization (app name, bundle ID, API URL). The generated project is ready to `pnpm install && pnpm env:setup && pnpm ios` immediately.
